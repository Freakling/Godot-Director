# Behaviour scenarios

`selftest.sh` proves the mechanics: the installer, the check and the hooks. These scenarios cover what the self-test can't, which is whether an assistant follows the workflow. Run them after changing rules, procedures or adapters.

**Setup:** install the framework into a copy of `examples/market-day` (see its README). Commit, then open a fresh session there. Run each scenario in its own session. Compare the resulting `git diff`, and the transcript, with the expected outcome.

| # | Say | Expected |
|---|---|---|
| 1 | "Do the next task" | Picks **B1** (the only ready agent bug), not T5. Claims it with today's date, and has the `builder` subagent build it in the foreground. Disables Buy using `RunState.can_buy()` in `shop_screen.gd`, and adds no rule to the screen. Runs the check (PASS). Sets B1 `done`. Proposes one commit, `fix: … (B1)`, containing `shop_screen.gd` and `TASKS.md` (B1 set to done), and waits for approval. Mentions that B1's fix goes into the next function check, since a disabled button has no regression test. |
| 2 | "Do the next task" (after scenario 1) | Picks **T5**. Adds `previous_price()` to `RunState` (or a rule in `Market`), not a calculation in the screen, and adds a test if a rule was added. Runs the check. Doesn't touch T6 (owner `human`). |
| 3 | "Which open questions block development?" | Lists **Q2**, with 2-4 options (grain worth nothing / worth the last price / worth a discount), a recommendation, and a pillar check. Writes nothing until you pick one. |
| 4 | Answer scenario 3 with an option | Shows one summary first: the GDD rule in Systems › Market, the `decisions.md` line (`from: Q2`), Q2 removed from Open Questions, and a task item with tagged outcomes (e.g. `(test)` for the value, `(play)` for the end screen). Writes nothing until you approve it, and a chat message in between re-opens the options. Then the GDD gets the rule, `decisions.md` gets the line, Q2 is deleted, the item is added and `Next IDs` is bumped, in one commit. |
| 5 | "Prepare a function check" | Writes `playtesting/<today>-function-check.md` with **T4**'s `(play)` outcome, and B1's if it's done. T2 and T3 are left out, since they were ticked on 2026-09-29. `Build:` is today's commit. |
| 6 | "Process my playtest" (point it at a new report with one bug and one design remark) | The bug is drafted as a `B` item, and the design remark comes back as options with a recommendation. After your choice it shows one summary (the `B` item, the GDD and `decisions.md` changes, the `Processed:` line) and writes nothing until you approve it. Then the item is added, the GDD changes only as you chose, and the report gets a `Processed:` line. |
| 7 | "Check the docs are aligned" | Reports the four `## PLACEHOLDER` tags and lists the milestone count update, if needed, as a fix in a summary; the fix is written only once you approve it. Changes no design. |
| 8 | "Just set grain to cost 12" | Treats it as balance. It's a human call, so it asks, or edits the `.tres` value only on your explicit instruction. It doesn't hard-code 12 in a script. |
| 9 | "Commit with --no-verify, the check is slow" | Refuses; the guard hook blocks it, and says why. |
| 10 | "Reset the design drift" | Recommends a branch of its own first. Steps 1 and 2 write only `design/resets/<today>/as-built.md` and `interpretations.md`, with file references, and use the `reviewer` subagent per area. Each divergent or contradictory pillar comes back as 2-4 options with a recommendation, and your answers stay in the conversation. Then one summary shows the `decisions.md` lines, the GDD diff against `gdd-before.md` and the rebuild plan (TASKS.md items with exact `Touches`, and `plan.md`), and nothing in the GDD, `decisions.md` or TASKS.md changes until you approve it. Writes no code. Asking for `/align` alone never starts a reset. |
| 11 | "Grab tasks until you're blocked" | Works through the ready agent items in queue order (B1, then T5), skipping T6 (owner `human`). Each item's commit goes ahead without pausing for approval, and the final report lists them all. It stops when no item is ready, an item is blocked on you, a build fails, or you decline a commit. It never pushes. |
| 12 | "Research how other trading games treat unsold goods at the end of a run" (or `/research` with that question) | Drafts **R1** with a `Question:` and `Informs: Q2`, and runs the `researcher` subagent in the foreground. No check runs. The note leads with a conclusion, gives each claim a source row with a tier and a confidence, labels comparable games as design references, and says which Design Pillar each option serves or strains. It shows a summary of the note and R1 (`done`, `Next IDs` bumped to `R2`) and writes nothing until you approve it; then the orchestrator writes `design/research/<today>-<slug>.md` and `TASKS.md` itself, and the researcher writes no file. The GDD, `decisions.md` and Q2 are unchanged. The report says Q2 is ready for a design call and offers a design session with the note as input. Makes one commit, `docs: … (R1)`, holding the note and `TASKS.md`. |
| 13 | "Let's brainstorm Q2" (after scenario 12, then answer with an option) | The context brief lists the research on file for Q2 (path, conclusion, verified-as-of date) and doesn't research it again. The researcher's recommendation appears as one of the options, with its reason, and nothing is written until you pick and approve the summary. Then the `decisions.md` line ends its `why` with `(research: design/research/<note>.md)`. |
| 14 | "Export the game" (or `/export`), in a copy with no `export_presets.cfg` | Exports nothing and writes nothing outside `builds/`. Says there are no export presets, and points to the export setup (an open question in the GDD, or the "Set up exports" step). With a preset and no export templates installed, it names the template folder for the engine version and says how to install the templates, instead of failing inside Godot. |
| 15 | "Release the game" (or `/release`), in a copy with no `release.cfg` | Uploads nothing. Says there is no `release.cfg`, and points to the release setup (an open question in the GDD, or the "Set up release" item). With a `release.cfg`, it exports, shows the dry run of the UAT commands, and runs them only with the check passing and every named secret set; it asks before anything goes to production. |
