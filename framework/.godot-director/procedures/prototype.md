# Prototype

Try a change fast, such as a mechanic, a feel or a screen, so the human can play it before it's built against the design. A prototype runs in its own session, in a git worktree beside the game on a `proto/<name>` branch, outside the loop in `rules.md`: no items, no records, no builder, no reviews and no check on its commits. What's worth keeping reaches main only through the harvest, as GDD changes, decisions, user stories (in a game that uses them) and items that are built from main like any other. `bash tools/prototype.sh` does the git steps; it never pushes, merges or deletes a branch. Prototypes start from, and are compared with, the `main` branch.

- `<name>`: start a prototype (Start).
- `list`: `bash tools/prototype.sh list` shows each `proto/` branch, its worktree folder (or `no worktree`) and its commits since main, and any gate file (see In a prototype session) that differs from main's.
- `harvest <name>`: turn one into GDD changes, decisions, user stories and items, then offer to remove it (Harvest).
- `remove <name>`: remove one without a harvest, when the human asks (Harvest, step 3).

## Start
In the main session; a prototype session doesn't start another.
1. **Name.** Lowercase letters, digits and dashes, such as `quick-dodge`. When the human gave none, propose one from what they want to try.
2. **Create it:** `bash tools/prototype.sh start <name>`.
   - It refuses an invalid name, and a name whose branch (`proto/<name>`) or folder already exists: say which, and ask for another name. An existing prototype goes on in its own session, or is harvested.
   - It also refuses, creating nothing, when a prototype's only gates aren't in place: main without the committed hooks and `tools/prototype.sh` (commit the Godot Director upgrade first), this clone whose pre-commit and pre-push hooks (in `.git/hooks`, or in `core.hooksPath` when it is set, relative to the repository top) don't run `.githooks/pre-commit` and `.githooks/pre-push` (run `bash tools/setup-clone.sh` here: it installs them, or leaves a hook of somebody else's that already runs ours, or prints the line to add to one that doesn't, which for a pre-push hook that reads the pushed refs on stdin, such as Git LFS's, takes the stdin-safe form: `refs="$(cat)"; printf '%s\n' "$refs" | bash .githooks/pre-push "$@" || exit 1`, with the rest of that hook reading from `$refs`), or no gitleaks on PATH. gitleaks is optional in every other commit, where a missing one is a note; a prototype skips the check, so the secrets scan is its only gate and it won't start, or commit, without one. Say which, and start again once it's fixed (`winget install gitleaks`, `brew install gitleaks`, or https://github.com/gitleaks/gitleaks#installing).
   - Exit 5: `origin/main`, as last fetched, has commits `main` doesn't, so it created nothing. Tell the human, and offer to bring main up to date first, with this checkout on main, by `git pull --ff-only` (they approve it), or to start from main as it is: `bash tools/prototype.sh start <name> --as-is`.
   - Otherwise it creates the worktree `../<game folder>-proto-<name>` on the new branch `proto/<name>` from `main` as this checkout has it, with no upstream, copies this clone's saved Godot path (`tools/godot_bin.local`) there, runs `bash tools/setup-clone.sh` there, and writes and commits its `PROTOTYPE.md`: the human's notes, under What we're trying, How it felt and What to keep. Uncommitted changes in this checkout don't go with it.
   - Exit 4: the prototype exists, but setup-clone or the first commit needs attention; show its lines. Don't open its session (step 4) until `bash tools/setup-clone.sh` passes in the new folder and `PROTOTYPE.md` is committed there.
3. **Before captures.** Where the game has screens (`bash tools/ui_capture.sh --list` names them), offer to capture the screens the prototype will change, now and in this checkout, as the before (`ui-design.md` › capture). A capture needs a display and opens a small window for a few seconds.
4. **Open its session,** once setup-clone has passed there. Start a session in the new folder where the tool can. Otherwise tell the human how: in Claude Code, open a new terminal there and run `claude`. Tell them too:
   - gitignored files aren't in the worktree: the saved Godot path was copied, and the first run there builds its own `.godot/` import cache (an import pass, so slower than usual). If they open the editor, they open that folder, not the main checkout's. Anything else the game reads from a gitignored file, such as local settings, they copy themselves (you never read or copy it);
   - notes go in its `PROTOTYPE.md` as they try things;
   - the harvest is back in this session: `/prototype harvest <name>` in Claude Code.

## In a prototype session
A session in a checkout that `bash tools/prototype.sh here` calls a prototype: a linked worktree on a `proto/` branch with `PROTOTYPE.md` at its root. Here the loop in `rules.md` is off:
- **No loop.** No items, claims or records (TASKS.md, AGENTS.md, `design/`), no builder and no reviews; a request for one belongs in the main session. Change what the human wants to try, directly and quickly: the smallest change that lets them feel it beats a complete one, since only what the harvest takes forward is built for real. The real build's habits (tests, autoplay scenarios, play log lines, drivable actions, rule classes and tunables in `rules.md` › Architecture defaults and Doing the work) are optional here; the harvest names what the prototype skipped.
- **The game can run.** Offer the human ways to try how it feels, and none of them gates the commit:
  - **A playtest:** they play it, in the editor or as the game runs, and tell you how it felt; write that in `PROTOTYPE.md`. "I just played, check the logs" works here too: `bash tools/log_review.sh --player` reads their session's log (`autoplay.md` › Review).
  - **Autoplay:** `bash tools/autoplay.sh smoke` (or a scenario) lets the game play itself through the change, and `bash tools/log_review.sh <run folder>` reads the run, as `autoplay.md` says. The signatures a review adds to `playtesting/signatures.tsv` are the prototype's; the harvest doesn't carry them.
  - **Tests:** `bash tools/check.sh --only tests/<file>.gd` runs one test file under the check's time limit; `bash tools/check.sh` runs the whole check, which gates nothing here.
  - A playtest report or function check (`playtest.md`, `function-check.md`) is a record, so it stays in the main session, after the harvest.
- **Commits need no approval.** Commit as often as helps, as `proto: <what changed>`. The pre-commit hook skips the project check in a prototype and still scans the staged changes for secrets; a finding blocks the commit, as anywhere, and so does a missing gitleaks, a `.gitleaksignore` or `.gitleaks.toml` that differs from main's and a staged `gitleaks:allow` comment (an inline allow hides a line from the scan), since the scan is the only gate here. Allowlisting a secret goes through the human in the main session: when gitleaks flags something you think is a false positive, ask them there; don't add a fingerprint.
- **Still on:** the guard, the secrets scan and Protected space (`director/` is the human's; never touch it).
- **The gates are the human's.** The hooks (`.githooks/`), the guard and settings (`.claude/`), `tools/prototype.sh`, `tools/setup-clone.sh`, `.gitleaksignore` and `.gitleaks.toml` are all that stand between a prototype's commits and the repository, so the Edit and Write guard refuses them here; don't change them by another route either. The harvest and `list` name any of them that differs from main's.
- **Nothing is pushed or merged.** Never push a `proto/` branch or its commits under another name (the pre-push hook refuses both), merge it into another or merge another into it. Nor is a prototype's build released or uploaded: `/release` runs in the main session.
- **Notes.** `PROTOTYPE.md` holds what was tried, how it felt and what to keep, in the human's words. Write down what they say there when they tell you, and commit it with the work; the harvest reads it.
- **After captures.** Where the game has screens, offer to capture the screens the prototype changed (`ui-design.md` › capture) when the human wants to compare: they land in this worktree's `design/ui/captures/` under the same names as the before in the main checkout's.
- **Done.** When the human has seen enough, commit everything, ask them to stop the prototype's game and close this session (and the editor on this folder), and send them back to the main session for the harvest.

## Harvest
In the main session, `harvest <name>`:
1. **Read.** `bash tools/prototype.sh harvest <name>` prints the commits, the files changed since main with the command for the diff, any gate file that differs from main's (tell the human, look at it first, and take none forward unchanged), the worktree's uncommitted changes and its `PROTOTYPE.md`; it changes nothing. The diff leaves out what isn't committed: ask the human to commit it in the prototype session first, or to harvest without it. Then read the diff it names, `git diff main...proto/<name>` (three dots: what the prototype changed, not what main gained since), file by file (`-- <path>`) when it's large. Show the after captures next to the before when both exist.
2. **Design.** Run `design.md` on them, as its Harvest a prototype section says: options, a recommendation, and the human decides. It proposes the GDD changes, decisions, user stories (with user stories on) and items, each naming the prototype. Nothing is filed without the human's answer.
3. **Remove.** Then offer to remove the prototype, and do only what the human says yes to:
   - **The worktree:** first ask the human to stop the prototype's game and close its session and its editor, since a folder in use can't be removed. Say that the folder goes with everything in it, ignored files too: the `.godot/` import cache, autoplay run folders and the after captures. Then run `bash tools/prototype.sh remove <name>`. It runs `git worktree remove`, which refuses a worktree with uncommitted or untracked changes; when it fails, show its lines, and ask the human to commit or delete those changes in the prototype session, or to free the folder. Never force it: `--force` discards them, and the guard blocks it. The branch keeps the commits, so an item's builder can still read the prototype's code.
   - **The branch:** a prototype is never merged, so `git branch -d` refuses it and deleting it takes `git branch -D`, which discards its commits; the guard leaves that to the human. Ask them in these words: "To delete the prototype's branch and its commits, run this in a terminal in the game folder: `git branch -D proto/<name>`." While an item that names the prototype isn't built yet, say that its builder can read the prototype's code only while the branch is kept.
